Boris — runbook (Pi-1)
======================

Boris runs as two systemd --user services plus two timers on pi-1,
started at boot via loginctl linger:

  boris-bridge.service     Go bridge (whatsmeow → SQLite + REST on :8080)
  boris-bot.service        Python admin_bot.py (polls SQLite, calls Claude)
  boris-watchdog.timer     fires boris-watchdog.service every 5 min
  boris-canary.timer       fires boris-canary.service daily at 10:15

Unit files live at ~/.config/systemd/user/ on the Pi. The Go bridge
binary lives at ~/projects/whatsapp-mcp/whatsapp-bridge/whatsapp-bridge
(separate clone of verygoodplugins/whatsapp-mcp); a symlink at
~/projects/tennis-pairings/whatsapp-mcp points there so admin_bot.py's
hard-coded path resolves.

Auto-recovery story
-------------------

bridge + bot have Restart=always with a 30s / 15s back-off and a
StartLimit cap of 20 attempts per 10 min. They self-heal from a
crash within ~30 s.

The bridge unit's ExecStartPre waits up to 60 s for DNS to resolve
web.whatsapp.com before launching the binary — covers the "service
started before the network was ready" race after a power-failure
reboot. Independent of that wait, Restart=always (not on-failure)
also catches the bridge's "tried 3 times to connect, gave up,
exited 0" path, which used to leave us dead after a boot race.

The watchdog (scripts/boris_watchdog.sh) is belt-and-braces for the
cases systemd can't see — bridge process up but HTTP wedged, unit
parked in "failed" state after exhausting StartLimit, or the bot
process alive but its main loop hung. Every 5 min it:

  - probes http://127.0.0.1:8080/ (any HTTP response = alive)
  - bridge: the first failed check only marks it down (a single miss
    is often a deploy or systemd's own restart already in progress);
    boris-bridge is restarted only if the next check fails too, i.e.
    after 2 consecutive failures
  - restarts boris-bot if systemctl says it is not active
  - also restarts boris-bot if its heartbeat file is stale: admin_bot
    touches .bot_heartbeat in the repo root on every poll loop, and
    if that file is older than BOT_STALE_SECS (default 1200 s, 20 min)
    while the bot has been up for longer than that, the main loop is
    taken to be hung. No heartbeat file yet means nothing to judge
  - posts a heads-up into the admin group when the bridge
    recovers after an outage >= 5 min (so the team knows there
    was a gap; ADMIN_GROUP_JID in .env)
  - greps the bridge journal for "Client outdated (405)" — the
    error WhatsApp returns when the whatsmeow library is too old.
    If found, touches a sentinel at /run/user/1000/boris-bridge-
    locked-out and logs at ERROR severity. We can't notify via
    WhatsApp in that state (the bridge IS what's locked out), so
    journalctl -p err is how it surfaces.

Tail the watchdog with:

    journalctl --user-unit=boris-watchdog -f

State across runs lives at /run/user/1000/boris-watchdog.state and
clears on Pi reboot, which is fine — a fresh boot is implicitly a
"recovered from down" event handled by the unit hardening above.

If the watchdog says "bridge LOCKED OUT", the recovery is to update
whatsmeow + rebuild the bridge:

    ssh pi-1
    export PATH=$PATH:/usr/local/go/bin
    cd ~/projects/whatsapp-mcp/whatsapp-bridge
    go get -u go.mau.fi/whatsmeow@latest
    go mod tidy && go build -o whatsapp-bridge .
    systemctl --user restart boris-bridge

Then commit go.mod/go.sum in ~/projects/whatsapp-mcp (the Pi has no
global git identity, so pass one):

    cd ~/projects/whatsapp-mcp
    git -c user.name="Geoff Chapman" -c user.email=gichapman@gmail.com \
        commit -am "Bump whatsmeow"

and refresh the patch copies (see below).

LOCAL BRIDGE PATCHES. ~/projects/whatsapp-mcp on the Pi is a clone of
the third-party github.com/verygoodplugins/whatsapp-mcp with local
commits on top that exist nowhere else (backup_pi.sh only saves the
bridge's .db files). Copies live in deploy/whatsapp-bridge-patches/
in this repo, as patches plus a tarball of the patched bridge source.
The base is upstream's "bump github.com/mattn/go-sqlite3 (#80)":
d362557 on the Pi, af660c2 in a fresh clone (upstream rewrote its
history in 2026; same files). Don't use origin/main as the base: after
a fetch it no longer shares history with the Pi's branch. After adding
a local bridge commit, refresh the copies from Windows (Git Bash):

    ssh pi-1 'cd ~/projects/whatsapp-mcp && rm -rf /tmp/bp && \
        git format-patch -q d362557 -o /tmp/bp && \
        git archive --format=tar.gz -o /tmp/bp/whatsapp-bridge-src.tar.gz HEAD whatsapp-bridge'
    rm -f deploy/whatsapp-bridge-patches/*.patch
    scp "pi-1:/tmp/bp/*" deploy/whatsapp-bridge-patches/

then commit them. To rebuild from scratch (new SD card) follow step 2
of scripts/restore_pi.md.

Independent of the watchdog, boris-canary.timer fires once a day
(10:15 local) and runs scripts/boris_daily_canary.py. The canary
posts "Boris daily test msg" to the Boris admin group via the
bridge's /api/send and trusts the bridge's HTTP response — a 200
with {"success": true} means whatsmeow's SendMessage returned
without error, which means the websocket to WhatsApp is alive and
WhatsApp ACK'd the message. (We don't poll messages.db: WhatsApp
doesn't echo own-originated messages back to the bridge.) If the
send fails, the canary retries every 30 s for up to 5 minutes
(CANARY_RETRY_INTERVAL_SECONDS / CANARY_RETRY_WINDOW_SECONDS in .env,
defaults 30 and 300) before giving up. That covers a reboot spanning
10:15: Persistent=true fires the missed run at boot, before the
bridge has reconnected to WhatsApp, and the retries give it time to
come up instead of raising a false alarm. If every attempt in the
window fails the service exits non-zero — `systemctl --user --failed`
will show boris-canary.service. The bot recognises the exact marker
string and silently drops it so the chat stays clean (see
CANARY_MARKER in bot_config.py).

The canary then reads CourtReserve the way a kickoff does: lists the
next 14 days' social sessions and fetches the first one's registrants.
A failure is retried once after 2 minutes
(CANARY_CR_RETRY_DELAY_SECONDS); if both fail it emails a separate
"CourtReserve read FAILED" alert and the service exits non-zero. This
catches a broken login or a CourtReserve site change before a kickoff
hits it. Tail with:

    journalctl --user-unit=boris-canary -f

Manual canary run:

    ~/projects/tennis-pairings/.venv/bin/python \
        ~/projects/tennis-pairings/scripts/boris_daily_canary.py

When SMTP_USER / SMTP_PASSWORD / ALERT_EMAIL are set in .env, a
canary failure (after the retry window) ALSO emails ALERT_EMAIL with a short diagnosis +
journalctl pointers. Email is best-effort: a delivery failure is
logged but doesn't change the canary's exit code. The systemd
EnvironmentFile= line on boris-canary.service is what loads the
SMTP credentials. Gmail SMTP needs an app password
(myaccount.google.com → Security → 2-Step Verification → App
passwords); a plain account password won't authenticate.

Connect
-------

    ssh pi-1        # home LAN only (pi-1.local, mDNS)
    ssh pi-1-ts     # from anywhere, over Tailscale

The commands in this file use pi-1; substitute pi-1-ts when away from
home.


Status / start / stop / restart
-------------------------------

    systemctl --user status  boris-bridge boris-bot
    systemctl --user start   boris-bridge boris-bot
    systemctl --user stop    boris-bot boris-bridge      # stop bot first
    systemctl --user restart boris-bot                   # most common


Live logs
---------

    journalctl --user-unit=boris-bot    -f
    journalctl --user-unit=boris-bridge -f

Use --since "10 min ago" or -n 200 for past output.


Sanity check
------------

Send `boris hi` from your phone in any of the admin groups
(ADMIN_GROUP_NAMES in admin_bot.py):
  - Thursday Tennis Organisers
  - Westside organisers of social tennis
  - Boris the tennis bot

Boris should reply within ~5 seconds, prefixed with
"From Boris the tennis bot: ".


WhatsApp QR re-link (when the linked-device session expires, ~14 days
of phone inactivity)
---------------------------------------------------------------------

The bridge prints a QR code in its journal on startup if re-link is
needed. To scan it:

    systemctl --user stop boris-bridge
    cd ~/projects/whatsapp-mcp/whatsapp-bridge
    ./whatsapp-bridge        # QR appears in this terminal — scan from
                             # WhatsApp -> Settings -> Linked Devices
                             # -> Link a Device, then Ctrl+C
    systemctl --user start boris-bridge


Notes
-----

- session_state.json (current evening's attendees + courts) is NOT
  cleared on restart. If you want a fresh start say `boris clear
  run` before the first command.
- Per-command Anthropic API usage is logged to the "Usage log" tab of
  the Google Sheet. Authoritative billing is at
  https://console.anthropic.com/.
- There is no automatic kickoff any more (the old Thursday 09:35
  scheduler was removed). A session starts when an organiser says
  `boris kickoff` (optionally naming the day, e.g. `boris kickoff
  for Saturday`).
- Code updates: `git pull` on the Pi, then
  `systemctl --user restart boris-bot` (and bridge too if Go side
  changed).
